# Publisher portal (v1): design

Status: ready for approval. Date: 2026-11-13. Base: `main` (after PR #2).

## Why

Publishing houses need a website where they can see **all of their sales and
money, with full transparency**, and where they **manage and publish their
books**. Transparency toward publishers is a core promise of Libraria, on top
of spec v2.1 §10. This first version builds the site and its money dashboard,
together with the book management the backend already supports. Uploading
EPUB files comes in the next project, with the DRM and storage security work.

## Decisions made with the user

- **A new web app** in the repo: React, Vite and TypeScript, in `portal/`. It
  talks to the existing `/api/v1`.
- **Layout A, a sidebar:**
  - **Money:** Overview, Sales, Earnings.
  - **Catalogue:** Books, "+ New book".
  - **Account:** Contract.
- **Books page.** It shows each book's status, price, copies sold and
  earnings, the idea taken from mockup C.
- **No payouts in v1.** How publishers are paid is undecided, so nothing says
  "owed" or "paid out".
- **The buyer's country** is captured on every sale from now on. Sales and
  Earnings can be broken down by country.
- **Team management is deferred,** because Libraria cannot send email yet.
  Admins keep creating publisher logins as today.
- **Login stays active across tabs and restarts** through a secure httpOnly
  cookie, with "Remember me". The portal and the API must share a site.
- **The portal is in Albanian and English.** The mobile reader app needs
  Albanian too, as the follow-up project after this one.

## Goals

- A publisher logs in and sees, for any period:
  - gross sales;
  - copies sold;
  - refunds;
  - VAT;
  - payment fees;
  - Libraria's commission;
  - their own earnings.

  These are shown in total, over time, per book and per country.
- Every sale is visible line by line and can be exported as CSV for the
  publisher's accountant.
- Every number in the portal reconciles exactly with the sales ledger.
  Summing the Sales lines gives the Overview and Earnings totals for the same
  filters.
- Publishers can create book drafts, edit details and price, and publish or
  unpublish.
- Admins can see any publisher's portal through a publisher picker.

## Non-goals (v1)

- Payouts, statements of what is owed, and bank details.
- EPUB upload and encryption (the next project). "Publish" still requires an
  asset, and until upload exists the portal says so.
- Team invitations and roles inside a publishing house.
- Mobile app changes, including the mobile app's Albanian translation, which
  is a separate follow-up project right after this one. Also other
  currencies, and languages other than Albanian and English.
- A deployment or hosting setup. The portal builds to static files, and where
  they are hosted is decided later.

## Anti-goals

- A publisher must never see another publisher's data, through any filter,
  export or URL.
- Money must never be computed in the browser. The portal displays numbers the
  backend computed from the ledger, and commission is never recomputed
  client-side.
- Totals must never disagree between pages for the same period and filters.

## Approaches considered

1. **A separate React app built with Vite (chosen).** It is a static site that
   uses the same API as the mobile app, keeps the API the single source of
   truth, and is the simplest to host.
2. **Next.js.** Its server rendering and SEO bring nothing to a portal behind
   a login, and it adds a server to run.
3. **Pages generated by Express.** Nothing extra to host, but interactive
   charts, filters and tables are clumsy, and the site and the API become
   coupled.

Reusing the mobile app on the web was ruled out: it is a phone reader, not a
desktop data tool.

## Design

### Data: buyer country (migration `0005_customer_country.sql`)

- Add `transactions.customer_country CHAR(2)`, nullable, ISO 3166-1 alpha-2
  and upper case. There is no backfill; older sales show as "Unknown".
- `payment_succeeded` provider events gain `countryCode: string | null`.
  `applyPayment` stores it, upper-cased and validated as `^[A-Z]{2}$`, and
  stores null otherwise.
- **Simulated provider:** the sandbox event accepts an optional `countryCode`.
  The default is `'DE'`, so the dev data has a country.
- **Paddle:** read the country from the transaction's address. Paddle's
  `transaction.completed` webhook may only carry an `address_id`. If so, fetch
  `GET /transactions/{id}?include=address` once, inside webhook processing.
  If that fetch fails, store null; never fail the payment because of it.
  - Mark the field path **VERIFY**, like the other Paddle fields, so it is
    confirmed on the first sandbox purchase.
  - The lookup happens before the database transaction opens, so no API call
    is made while rows are locked.

### Reporting rules (one definition, used by every endpoint)

- **A sale** is a `transaction_items` row whose transaction is in `paid`,
  `partially_refunded`, `disputed` or `refunded`. Fully refunded items stay
  in, so refunds are visible.
- **Period:** a sale belongs to the period of its transaction's `paid_at`, in
  **UTC**. Refunds are counted against the sale's own period, not the date of
  the refund. With no payouts yet, restating a past month when a refund
  arrives is acceptable. Payout statements will later need refunds dated
  when they happen.
- **Metrics,** all integer EUR cents:
  - `grossCents` is the sum of `unit_price_cents`;
  - `refundsCents` is the sum of `refunded_cents`;
  - `taxCents` is the sum of `tax_cents`;
  - `feeCents` is the sum of `provider_fee_cents`;
  - `commissionCents` is the sum of `platform_commission_cents −
    platform_commission_reversed_cents`;
  - `earningsCents` is the sum of `publisher_earnings_cents −
    publisher_earnings_reversed_cents`;
  - `copies` is the count of items not fully refunded (`refunded_at IS
    NULL`), and `refundedCopies` is the count of fully refunded items.
- Null shares or fees count as 0, and the item's Sales line carries a
  `split` state saying why, so the gap is visible rather than silent:
  - `'pending'`: the provider has not reported the fee yet;
  - `'no_rate'`: the item was checked out before commission rates existed and
    will never be split.

  Both states are already flagged for admin review on the transaction. v1 has
  no automatic re-split. If Paddle turns out never to send the fee, that shows
  up in the VERIFY sandbox test and becomes its own fix.
- **Line status is the item's own status, never the order's,** so a publisher
  never learns about another publisher's book in the same order:
  - `refunded` if `refunded_at` is set;
  - otherwise `partially_refunded` if `refunded_cents > 0`;
  - otherwise `disputed` if the transaction is disputed, since a dispute covers
    the whole payment, this book included;
  - otherwise `paid`.

  The `status` filter uses these four values.
- **The Earnings breakdown always adds up.** Our records do not reduce VAT and
  fees on refunds, so the table does not subtract refunded gross from them.
  It reads:

  | Line | Calculation |
  | --- | --- |
  | Gross sales | |
  | − VAT | |
  | − payment fees | |
  | **= net** | |
  | − Libraria commission | at sale |
  | **= earnings at sale** | |
  | − refund reversals | earnings reversed by refunds |
  | **= earnings** | |

  Every row is a stored sum, so the table reconciles exactly. Refunded gross,
  meaning the money returned to readers, is shown beside it as information,
  not as a subtraction. A note says that VAT and fees are shown as at sale
  time. (Recording the VAT and fee returned on each refund belongs with the
  payouts project.)
  - To support this, `Metrics` exposes both the at-sale and the reversed
    figures: `commissionAtSaleCents`, `commissionReversedCents`,
    `earningsAtSaleCents`, `earningsReversedCents`. `commissionCents` and
    `earningsCents` are the after-reversal values.
- The rules live in one backend module, `backend/src/reports/`, as one SQL
  base query or view that the summary, breakdown, ledger and CSV queries all
  build on. This is what keeps the totals consistent.

### Backend endpoints

All endpoints sit under `/api/v1/publisher/reports/`, with the same auth and
tenant scoping as `/publisher/*`:
- publishers are always scoped to their own house;
- admins must pass `publisherId`;
- `from` and `to` are ISO dates, inclusive of `from` and exclusive of `to`,
  in UTC. The range is required and at most 3 years.

| Endpoint | Returns |
| --- | --- |
| `GET /summary?from&to&granularity=day\|week\|month` | `{ totals: Metrics, series: [{ periodStart, ...Metrics }] }`. Periods with no sales are included, with zeros. |
| `GET /by-book?from&to` | `{ rows: [{ book: {id,title}, ...Metrics }] }`, sorted by gross, descending |
| `GET /by-country?from&to` | `{ rows: [{ country: 'DE' \| null, ...Metrics }] }` |
| `GET /sales?from&to&bookId?&country?&status?&page&limit` | Sales lines: `paidAt`, `transactionId`, book, country, item `status`, `unitPriceCents`, `taxCents`, `feeCents`, `commissionRateBps`, `commissionCents`, `earningsCents`, `refundedCents`, `split` (`'done' \| 'pending' \| 'no_rate'`). Newest first, paginated. |
| `GET /sales.csv` (same filters, no paging) | `text/csv`. It has a header row, one row per sales line, amounts in euros with 2 decimals and a `.` decimal separator, and dates in ISO UTC. It is streamed or capped at 50,000 rows. |

The reader's identity (user id, email) never appears in any report or export.

**CORS:** a new env setting, `CORS_ORIGINS`, holds a comma-separated list of
allowed origins and is empty by default. Responses to those origins allow
credentials (cookies). In development the portal uses Vite's proxy, which
makes it same-origin, so it needs no CORS. In production the setting allows
the portal's origin to call the API.

### Portal login: secure cookie (chosen by the user)

The portal does not keep the login where page scripts can read it.

- **Login:** `POST /api/v1/auth/portal/login` takes `{ email, password,
  rememberMe }`.
  - It checks the password exactly like `/auth/login`.
  - Only the `publisher` and `admin` roles get in. Others get `403
    PORTAL_ACCESS_DENIED`, which is a new error code.
  - On success it sets the cookie `libraria_portal`, containing a signed
    access token with the same claims as today. The cookie is `HttpOnly`,
    `SameSite=Lax`, `Path=/api`, and `Secure` whenever `NODE_ENV=production`.
  - It returns `{ user }` and never the token.
- **Lifetime:**
  - with "Remember me", the cookie and the token last **30 days**;
  - without it, it is a browser-session cookie with a **12-hour** token.

  These are new env settings, `PORTAL_SESSION_HOURS=12` and
  `PORTAL_REMEMBER_DAYS=30`.
- **Logout:** `POST /api/v1/auth/portal/logout` clears the cookie. Tokens are
  stateless, so a copied token stays valid until it expires. Revocation is a
  later hardening step.
- **Session check:** `GET /api/v1/auth/me` works with the cookie, so the
  portal can find out on load whether someone is logged in.
- **Authentication:** `requireAuth` accepts a Bearer token (the mobile app,
  unchanged) or the portal cookie. If both are present, Bearer wins.
- **Protection against forged requests:**
  - any request authenticated by the cookie that changes something (not GET,
    HEAD or OPTIONS) must carry the header `X-Libraria-Portal: 1`, or it gets
    `403 CSRF_CHECK_FAILED`, a new code;
  - a page on another site cannot add that header without a CORS preflight,
    which `CORS_ORIGINS` refuses;
  - together with `SameSite=Lax`, this closes cross-site forms and scripts.
- **Hosting constraint (recorded in the README):** the portal and the API must
  be served from the **same site**, for example `portal.libraria.com` and
  `api.libraria.com`, or the same domain behind one proxy. Otherwise browsers
  will not send the cookie.

### Portal app (`portal/`)

- **Stack:** Vite, React and TypeScript in strict mode, with React Router.
  Charts use one charting library, Recharts unless the builder has a strong
  reason otherwise. Server data is cached with TanStack Query. Styling uses
  plain CSS with a small set of colour tokens matching the mobile app (blue
  `#2563EB`, green `#059669`, grey scale).
- **Login:** the page has email, password and a "Remember me" box, and uses
  the cookie login above.
  - Every request is sent with `credentials: 'include'` and the
    `X-Libraria-Portal: 1` header.
  - On load the portal calls `GET /auth/me` to restore the session.
  - `PORTAL_ACCESS_DENIED` shows "This portal is for publishing partners".
  - A 401 response returns to the login page with a "session expired"
    message.
  - The portal never stores a token itself.
- **Admin publisher picker:** it appears in the top bar for admins only and
  sets `publisherId` on every call.
  - It is fed by a new endpoint, `GET /api/v1/admin/publishers`, which returns
    `{ publishers: [{id, name}] }` sorted by name, for admins only.
  - Admins may also edit books in the portal, as support staff, which the API
    already allows. The Books list is scoped to the picked publisher.
  - The book write routes (PATCH, asset, publish, unpublish) currently ignore
    `publisherId` for admins. For an admin passing `publisherId`, they must
    check that the book belongs to that publisher and return 404 otherwise,
    with tests, so a stale picker can never edit the wrong house's book.
- **Pages:**
  - **Overview:**
    - a period selector (this month, last month, last 90 days, this year,
      custom);
    - four headline numbers (gross sales, copies, refunds, your earnings),
      each with the change against the previous period of equal length;
    - a sales-over-time chart and the top 5 books.
  - **Sales:** the filterable, paginated table of sales lines and an "Export
    CSV" button. Lines whose `split` is not `'done'` show "Fee pending" or
    "Not split (sold before your contract)".
  - **Earnings:**
    - a per-month table that takes gross sales down to earnings: refunds,
      VAT, fees, commission, and finally earnings;
    - toggles to view the same breakdown by book or by country;
    - a short note explaining the rules from "Reporting rules".
  - **Books:**
    - a list with status, price, copies and earnings (from the existing
      `GET /publisher/books`), with search and status filter;
    - a "+ New book" form;
    - an edit page with publish and unpublish. "Publish" on a book with no
      file explains that file upload is coming.
  - **Contract:** the current rate and its history, from `GET
    /publisher/contract`.
- **Languages: Albanian and English** (chosen by the user).
  - **Switcher:** a Shqip/English switcher sits in the top bar and on the
    login page. The choice is remembered in `localStorage`. On a first visit,
    the portal uses Albanian if the browser's preferred languages include `sq`,
    and English otherwise.
  - **Translation files:** every string the user sees comes from a
    translation file per language, `portal/src/i18n/sq.json` and `en.json`,
    through one lightweight library (react-i18next unless the builder has a
    reason otherwise).
  - **Keys:** each language has exactly the same keys, enforced by a unit
    test.
  - **Error messages** are translated in the portal by API error `code`,
    with a generic fallback; the backend stays English.
  - **Formats:** money, numbers and dates follow the language through `Intl`
    with locale `sq-AL` or `en-IE` (for example "1.234,50 €" and "€1,234.50").
    Country names come from `Intl.DisplayNames` in the same language, with a
    translated "Unknown" for null.
  - **CSV export:** the client asks for `sales.csv?lang=sq|en`. The column
    headers are in that language, but values keep one fixed machine format
    (`1234.50`, ISO dates, status codes) so spreadsheets read them
    consistently.
  - **Albanian text:** written by the builder and **reviewed by the user
    before launch**.
  - **Shared files:** the translation files are portal-only. The mobile app
    gets its own files in its follow-up project; the two apps share almost no
    text.
- **Errors:** the portal branches on the API's error `code`. A failed request
  shows a retry state, never a blank page.

### Tooling

- `portal/` has its own `package.json`, with `dev`, `build`, `typecheck`,
  `lint` and `test` scripts. Lint uses Biome with the same settings as the
  backend.
- A **portal** job is added to CI: typecheck, lint, tests and build.
- The portal is not added to docker compose. It runs with `npm run dev`
  against the API, keeping Docker light.
- The README gets a Portal section.

### Testing

- **Backend integration tests:**
  - reports are tenant-isolated: publishers can't read others, a publisher's
    `publisherId` is ignored, and admins must name one;
  - the same filters give the same totals on every page: summary totals equal
    the sum of the Sales lines, which equal the sum of the by-book and by-country
    rows;
  - period edges in UTC (a sale at 23:30 UTC on the 31st belongs to that
    month);
  - empty periods return zeros;
  - CSV output: header, decimals, escaping of titles with commas or quotes;
  - sales without a fee are marked `split: 'pending'`;
  - in a multi-publisher order where another publisher's book was refunded,
    this publisher's line still says `paid`;
  - the Earnings rows add up exactly after full and partial refunds;
  - an admin passing `publisherId` cannot edit another publisher's book;
  - `GET /admin/publishers` is admin-only;
  - country is stored from the sandbox and missing country gives
    "Unknown"/null.
- **Backend auth tests:**
  - portal login sets an HttpOnly cookie and never returns the token;
  - readers get `PORTAL_ACCESS_DENIED`;
  - "Remember me" changes the cookie lifetime;
  - logout clears the cookie;
  - a write request authenticated by the cookie without `X-Libraria-Portal`
    gets `CSRF_CHECK_FAILED`;
  - Bearer-token mobile requests are unaffected;
  - CORS allows only `CORS_ORIGINS`, with credentials.
- **Portal tests,** with Vitest and Testing Library:
  - money and date formatting in both languages;
  - both translation files have the same keys;
  - the language switcher and its first-visit default;
  - login gating by role;
  - a reports page rendering API data.

  More is left to the builder.

## Calls I made (to check)

- Times and periods are in **UTC**, not a European time zone.
- Refunds count in the **sale's** period, so past months can change.
- VAT and fees are shown as at sale time, not reduced by refunds.
- The cookie login lasts 30 days with "Remember me" and 12 hours without
  it. Logout clears the cookie, but a stolen token is not revoked until it
  expires.
- On a first visit, the language is Albanian if the browser prefers it, and
  English otherwise.
- CSV headers follow the chosen language. Values keep one machine format.
- The CSV export is capped at 50,000 rows per export.
- The Earnings table takes gross down to net, then commission, then
  earnings at sale, then refund reversals, with refunded gross shown beside
  it. This is so it always adds up while our records keep VAT and fees as at
  sale time.
- A Sales line shows the book's own status, not the whole order's.
- Admins can edit books for the publisher picked in the portal, and the
  backend checks the picked publisher on every book write.
- Sales with no fee or no rate are labelled, not re-split automatically.

## Left to the builder

- Exact component structure, the routing layout and the charting details.
- Whether the shared report rules are a SQL view or a query builder function,
  as long as there is exactly one definition.
- How the portal's look follows the mockups, within the colour tokens above.
